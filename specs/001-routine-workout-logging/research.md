# Research: 운동 루틴 관리 및 세트 기록

**Feature**: `001-routine-workout-logging` | **Date**: 2026-11-14 | **Plan**: [plan.md](./plan.md)

각 항목은 결정 / 근거 / 대안 순서다. R1~R8은 `~/Documents/todo-app`의 `specs/002-personal-task-manager/research.md`에서 가져온 결정이고, 이 앱에 맞게 달라진 점만 적었다. R9 이후는 이 기능에서 새로 정한 것이다.

## 재사용하는 결정 (todo-app)

### R1. 클라이언트 형태: 설치형 웹 앱(PWA)
- **결정**: 홈서버가 제공하는 PWA 하나. "홈 화면에 추가"로 설치한다. 시작할 때 `navigator.storage.persist()`를 요청한다.
- **근거**: 코드베이스가 하나이고 개발자 계정이 필요 없다. 홈 화면에 설치한 웹 앱은 Safari의 "7일 미사용 시 저장소 삭제"에서 제외된다. 헌법 V(추후 Capacitor 래핑)와도 충돌하지 않는다.
- **todo-app과 다른 점**: Web Push 알림이 없으므로 구독·VAPID·푸시 관련 코드와 API를 모두 뺀다.
- **대안**: SwiftUI 네이티브, 처음부터 Capacitor. 이 기능에는 과하다. 기각.

### R2. 언어와 런타임
- **결정**: 서버·클라이언트·공유 로직 모두 TypeScript. 서버는 Node에서 type stripping으로 직접 실행(erasable syntax만). 클라이언트는 esbuild 번들. 개발 환경은 Node ≥ 22.18, 배포 서버는 Node 24.
- **근거**: 병합·검증·볼륨·단위 변환을 `shared/`에 한 번만 구현해 서버와 클라이언트 결과가 같게 한다.

### R3. 서버 저장소: SQLite
- **결정**: Node 내장 `node:sqlite`, WAL, `/var/lib/fitness/fitness.db`, `PRAGMA user_version`으로 마이그레이션.
- **확인 필요**: 구현 시작 때 대상 Node에서 플래그 없이 동작하는지 확인(개발 머신 v22.21은 todo-app에서 이미 사용 중). 안 되면 `better-sqlite3`를 유일한 런타임 의존성으로 추가하고 plan의 Complexity Tracking에 기록한다.

### R4. 홈서버 배치와 TLS
- **결정**: todo-app과 같은 방식. 전용 LXC(또는 기존 서버의 별도 서비스)에서 Caddy가 `tls internal`로 443을 받아 정적 파일과 `/api/*` 프록시(→ `127.0.0.1:<포트>`)를 처리한다. 주소는 `fitness.home.arpa`(예시). todo-app과 같은 호스트에 둘 경우 Caddyfile에 사이트 블록만 추가하고 서비스·DB·포트(예: 8081)는 분리한다.
- **근거**: 외부 서비스에 의존하지 않고 인증서가 자동 갱신된다. 기기에는 todo-app 때 설치한 Caddy 루트 인증서를 같은 CA면 그대로 쓸 수 있다.
- **미정(사용자 확인)**: todo-app과 같은 LXC에 둘지 별도 LXC로 할지. 어느 쪽이든 앱 코드는 같다. install.sh는 두 경우 모두 동작하게 한다.

### R5. 집 밖 접속: 기존 WireGuard
- **결정**: 포트 포워딩 없이 WireGuard로 같은 주소에 접속한다. 연결이 없으면 로컬에 쌓고 나중에 동기화한다(헬스장 시나리오와 동일).

### R6. 동기화 모델: 레코드 단위 LWW + HLC
- **결정**: 레코드마다 하이브리드 논리 시계(HLC) `version`을 붙이고 큰 쪽이 이기는 LWW로 병합한다. 서버가 단조 증가 `seq`를 매기고 클라이언트는 `seq` 커서로 변경분을 받는다. push는 멱등이다. 레코드는 4종(exercise, routine, session, settings)이며 하나의 `seq` 번호 공간을 공유한다.
- **서버 복원 감지**: 서버 cursor가 저장된 값보다 작으면 모든 로컬 레코드를 dirty로 표시하고 cursor를 0으로 되돌려 push→pull 한다.
- **근거**: 사용자 1명이라 충돌이 드물고, 항목 단위 LWW로 충분하다(YAGNI).
- **대안**: CRDT, PouchDB. 과하다. 기각.

### R7. 실시간 반영: SSE
- **결정**: `GET /api/events`가 새 `cursor`만 알리고 클라이언트가 pull한다. 보조로 `visibilitychange`, `online`, 앱 시작, SSE가 끊긴 동안 30초 간격 pull.

### R8. 기기 등록과 인증
- **결정**: 서버 CLI `fitness-admin pair --name`이 10분짜리 일회용 코드를 발급하고, 기기가 코드와 클라이언트가 만든 `deviceId`를 보내 등록한다. 기기별 세션 쿠키(`HttpOnly; Secure; SameSite=Strict`), 토큰은 SHA-256 해시만 저장, 쓰기 요청은 `X-Fitness-Client: 1` 헤더 필수(CSRF). `FITNESS_DEV=1`일 때만 `Secure` 제외.
- **근거**: 소유자 한 명이라 계정·비밀번호가 필요 없다(FR-017).

## 이 기능에서 새로 정하는 결정

### R9. 레코드 구성: 세션 하나 = 레코드 하나 (세트 내장)
- **결정**: `session` 레코드가 종목별 기록과 세트 배열을 모두 내장한다. 루틴도 종목 구성(순서 있는 항목 배열)을 내장한다. 세트·루틴 항목은 독립 레코드가 아니다.
- **근거**: 세션 진행 중에는 한 기기에서만 편집하므로 항목 단위 병합이 필요 없다. 세션 하나가 원자적으로 저장·동기화되어 "세트 일부만 반영된 세션"이 생기지 않는다. 세션 크기는 수 KB라 푸시 한도(1 MiB/500건)에 문제없다.
- **알려진 한계(스펙이 허용)**: 같은 완료 세션을 두 기기에서 오프라인으로 동시에 수정하면 나중 수정이 이긴다. 필드 단위 병합은 하지 않는다.
- **대안**: 세트마다 레코드(쓰기 증폭, 부분 반영 위험), 세션+세트 2종(동기화 순서 의존). 기각.

### R10. 진행 중 세션 모델
- **결정**: `status: "active" | "completed"`. 진행 중 세션은 동시에 최대 하나이며, 입력할 때마다 즉시 IndexedDB에 저장한다(디바운스 없이 트랜잭션). 앱을 다시 열면 `active` 세션을 찾아 "이어서 기록" 화면으로 복원한다. 진행 중 세션도 일반 레코드처럼 동기화되지만, 다른 기기가 이어받는 것은 지원하지 않는다(진행 중 세션은 `startedBy` 기기에서만 편집 가능, 다른 기기에서는 읽기 전용 표시).
- **기기 간 동시 진행 중 세션**: 폰과 PC가 오프라인에서 각각 세션을 시작하면 동기화 후 진행 중 세션이 2개가 될 수 있다. "최대 1개"는 **기기 단위** 규칙이다(한 기기는 자신이 시작한 진행 중 세션을 하나만 가진다). 서버는 여러 개를 허용하고, 앱은 `startedBy`가 현재 기기인 진행 중 세션만 "이어서 기록"으로 보여 주며 다른 기기의 진행 중 세션은 기록 목록에 "다른 기기에서 진행 중"으로 읽기 전용 표시한다.
- **로컬 전용 사용**: 앱은 페어링 없이도 완전히 동작한다(모든 데이터는 IndexedDB에 저장). 페어링은 설정 화면에서 선택하며, 페어링하면 그때까지 쌓인 레코드가 모두 dirty로 서버에 올라간다.
- **근거**: 유실 방지(헌법 II)와 단순성. 기기 간 이어받기는 요구되지 않았다.
- **엣지**: 오래 방치된 진행 중 세션(**마지막 활동 후** 12시간 초과; 마지막 활동 시각은 `version`(HLC)의 시각이라 세션을 계속 고치는 중이면 방치로 보지 않는다)은 다음 실행 시 "이어하기 / 종료 / 폐기"를 묻는다. 폐기는 툼스톤이다. 완료 세트가 0개인 세션을 종료하면 저장 여부를 묻고, 저장하지 않으면 폐기한다.

### R11. 무게 단위와 정밀도 (SC-006)
- **결정**: 무게는 `weightKg`(number)로 저장한다. 사용자 설정이 lb이면 입력값을 `kg = lb × 0.45359237`로 변환해 저장하고, 표시할 때 `lb = kg ÷ 0.45359237`을 **소수 둘째 자리로 반올림하고 불필요한 끝자리 0은 제거**한다(예: 45.00 → `45`, 45.50 → `45.5`, 100.25 → `100.25`). kg 표시도 같은 규칙(소수 둘째 자리, 끝자리 0 제거)이다. 저장 전에 kg 값을 소수 넷째 자리로 반올림한다. 입력 허용 범위는 0 이상 1000 이하(kg 기준), 입력 단위(kg/lb) 모두 소수 둘째 자리까지.
- **근거**: 한 가지 기준 단위로 저장해야 단위를 바꿔도 기록이 일관된다. 입력이 소수 둘째 자리까지이므로 표시도 둘째 자리까지여야 입력한 값이 그대로 보인다(SC-006). kg를 넷째 자리로 저장하면 lb 둘째 자리 입력이 왕복(lb→kg 저장→lb 표시)에서 손실되지 않는다는 것을 단위 테스트로 검증한다. (스펙 Edge Cases의 "표시 단위만 바꾼다"를 이 방식으로 구현한다.)
- **대안**: 입력 단위 그대로 저장 + 단위 필드 병기(집계 때마다 변환 필요). 기각.

### R12. 입력 검증
- **결정**: 클라이언트와 서버 양쪽에서 같은 `shared/model.ts` 검증을 쓴다. 규칙: 무게 0 이하가 아니라 **0 이상**(맨몸 운동 허용) 1000kg 이하, 횟수 **1 이상 정수** 999 이하, 루틴·종목 이름은 공백 제거 후 1~60자(코드 포인트), 루틴당 종목 최대 50개, 종목당 세트 최대 50개, 종목 목표 세트 수 1~20.
- **근거**: FR-007. 비정상적으로 큰 값은 오타 방지 목적이다.

### R13. 직전 값 미리 채우기 (FR-006)
- **결정**: `prefill(exerciseId, sessions)`: 완료된(`status=completed`, 미삭제) 세션 중 가장 최근에 그 종목을 포함한 것의 **완료된 세트**를 순서대로 가져와 새 세션의 같은 번호 세트에 무게·횟수를 채운다. 직전 세트 수보다 많은 세트는 마지막 세트 값을 복사한다. 이력이 없으면 비워 둔다(횟수 기본 미리 채움 없음). 채운 값은 "미완료" 상태이며, 체크(완료) 탭 한 번으로 확정한다.
- **근거**: 한 세트 5초 목표(SC-001). 계산은 `shared/prefill.ts` 순수 함수로 둔다.

### R14. 클라이언트 저장소 구조 (IndexedDB)
- **결정**: object store: `exercises`, `routines`, `sessions`, `settings`, `meta`(cursor, deviceId, dirty 표지). `sessions`는 `completedAt` 인덱스와 `status` 인덱스를 둔다. 기록 목록은 인덱스 커서로 최신순 읽기, 종목 이력은 세션을 순회해 계산한다(수천 건 규모에서 SC-005 충족; 부족하면 종목별 인덱스를 추가).
- **근거**: 규모가 작아 별도 인덱스 테이블이 필요 없다(YAGNI).

### R15. 기본 운동 종목
- **결정**: 부위(가슴·등·어깨·하체·팔·코어·유산소 등)별 기본 종목 약 40개를 `shared/seed-exercises.ts`에 두고, 첫 실행 때 고정 id(결정적 UUID)로 `exercises`에 넣는다. 사용자 정의 종목은 `custom: true`. 기본 종목도 이름 수정·삭제 가능(툼스톤). 시드를 동기화로 중복 생성하지 않도록 id가 고정이다.
- **시드 버전**: 시드 레코드는 항상 지는 고정 최소 HLC(`000000000000000-000000-seed`)를 `version`으로 가지며 **dirty 표시를 하지 않는다**(서버로 push하지 않는다). 그래서 한 기기에서 시드 종목을 수정·삭제한 레코드(더 큰 version)가 다른 기기의 시드를 항상 이기고, 삭제한 시드 종목이 새 기기의 첫 실행으로 되살아나지 않는다. 사용자가 시드 종목을 수정하면 일반 레코드처럼 새 version을 발급받아 동기화된다.
- **근거**: FR-003. 기능 2(가이드)가 `exercise.id`/`bodyPart`로 미디어를 연결할 수 있다.

### R16. 내보내기와 전체 삭제 (FR-014)
- **결정**: 내보내기는 클라이언트가 로컬 데이터를 JSON 파일로 내려받고(`shared/export.ts`), 서버 기준 사본은 `fitness-admin export`로 받는다. 형식은 `{ "format": "fitness-export", "version": 1, ... }`. 전체 삭제는 루틴·세션·직접 만든 종목·설정을 내용을 비운 툼스톤(id·version·deleted·updatedBy만 유지)으로 바꾸고 동기화한다. 그 결과 서버와 모든 기기에서 운동 데이터 내용이 사라진다.
- **기본 종목은 남긴다**: 기본 종목은 앱의 일부라 지우지 않는다(지우면 삭제 후 앱에 종목이 하나도 없다). 사용자가 고치거나 지운 기본 종목은 기본값으로 되돌려 새 version 으로 올려, 다른 기기에도 기본값이 퍼지게 한다. 건드리지 않은 기본 종목은 그대로(시드 버전, 올리지 않음).
- **근거**: 별도 삭제 API 없이 기존 동기화 경로를 재사용한다(원칙 V).

### R17. 화면과 접근성
- **결정**: 하단 탭 3개(루틴 / 기록 / 설정), 세션 진행 화면은 세트 행(무게·횟수 숫자 입력 + 완료 체크)을 한 줄로 두고 `inputmode="decimal"`/`numeric`을 쓴다. 터치 영역 최소 44px, 색에만 의존하지 않고(완료는 체크 아이콘과 텍스트), 동기화 상태·오류는 `aria-live`. axe 자동 점검과 320px 폭 E2E를 둔다.
- **근거**: 헌법 I, 기술 제약(WCAG 2.1 AA).

### R18. 테스트 전략
- **결정**: 테스트 먼저: (1) 단위(`shared/tests`): hlc, merge, model 검증, volume, units 왕복, prefill. (2) 계약(`server/tests/contract`): [sync-api.md](./contracts/sync-api.md) 목록. (3) E2E(Playwright): 스토리 US1~US4마다, 오프라인·새로고침 복원·서버 재연결 동기화 포함, axe 점검. (4) 클라이언트 동기화 엔진은 `fake-indexeddb`로 단위 테스트.

### R19. 배포
- **결정**: `deploy/install.sh`(멱등)가 Node, Caddy, 앱 파일, systemd 유닛(`fitness.service`, 전용 사용자 `fitness`, `StateDirectory=fitness`, `ProtectSystem=strict`)과 `fitness-admin` 명령을 설치한다. 알림용 아웃바운드 허용 설정은 필요 없으므로 `IPAddressDeny=any`를 걸 수 있다(Caddy는 별도 프로세스). 백업은 `fitness-admin backup`(SQLite 온라인 백업)을 cron에 건다.
